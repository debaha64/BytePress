# Тесты

`tests/` — единственное специальное место Product Unit для исполняемых модулей технической и регрессионной проверки Harness. Тест является механическим доказательством контракта, принадлежащего Markdown-документу; он не является пользовательским CLI или самостоятельным источником полномочий.

## Наборы

| Модуль | Что проверяет |
|---|---|
| `test_project_profile.py` | схема v1, Slug/PartSlug, состав проекта, части и объявления проверок без исполнения команд |
| `test_new_project.py` | Project Start `preview/apply`, фиксированная поставка, промежуточное создание и восстановление, неизменность источника и настоящая интеграция проверяющих инструментов |
| `test_check_workspace.py` | универсальные границы Workspace на нейтральных самостоятельно созданных заготовках |
| `test_check_product.py` | универсальный состав продукта и явно запускаемый встроенный механизм собственных проверок |
| `test_harness.py` | состав и квалификация самой поставки BytePress, VERSION, манифест Project Start, различия способов переноса и отсутствие третьего проверяющего CLI |
| `test_release_preflight.py` | требования REQ-REL-001..009 и границы выпускных свидетельств |
| `test_workspace_update.py` | ограниченное обновление Workspace по существующей процедуре изменений |

## Запуск и происхождение

Канонический запуск из корня свежей внешней копии поставки BytePress:

```bash
python3 -B -m unittest discover -s tests -p 'test_*.py'
```

Для свидетельств о защищённом исходнике сначала контролируют `PYTHONPATH` и подтверждают свежий корень, рабочий каталог, тестовые модули, `new_project.py`, `project_profile.py`, происхождение исполняемых файлов и модулей обоих проверяющих инструментов и очистки продукта. Затем `new_project.py` создаёт внешний Workspace, а развёрнутые `check_workspace.py` и `check_product.py` запускаются из его `tools/`. Переменная `BYTEPRESS_LIVE_SOURCE_ROOT` передаёт точный путь исходного продукта для отрицательных проверок происхождения.

Изменение поведения требует предварительного написания тестов: принятые `REQ/INV/SCN` → содержательный RED → минимальная реализация → целевой GREEN → зависимые проверки и полная регрессия. Нейтральная заготовка не создаёт требования, точку контроля, маршрут или полномочия владельца. Временные проверки используют `mktemp -d` или временный каталог вне поставки; постоянный `fixtures/` не создаётся. Порядок и критерии принадлежат [verify-work](../sops/verify-work.md).

## Существенные границы регрессии

- Исполнимый SDLC: действительные завершение, передача результата и полномочия; отсутствие свидетельств; пропуск контрольной отметки; преждевременные или сохранённые полномочия; обход точки решения владельца; разделение Verification, Validation, Product Acceptance и Release Authorization. Полная исходная база проверяет фактические создание, обновление, удаление, сохранность, типы и режимы доступа. E2E Project Start создают синтетические записи только внутри временной цели и не создают решения владельца в настоящем Workspace.
- Выпускные свидетельства: репозиторий, правила и цепочка участников; скрытый и пустой списки обхода; ответ `404` классической защиты и отдельно доказанное администратором отсутствие настройки; ограниченные свидетельства человека; GET без оболочки и утечек; краткие отчёты; точное контрольное чтение и правила переноса. `test_harness.py` проверяет настоящую поставку Project Start без автоматического запуска, включая запуск поставленных тестов предварительной проверки в свежем Workspace без Git/GitHub. Заготовки нейтральны, записи в настоящий GitHub отсутствуют.
- Workspace Update: автономные заготовки всех режимов SoT, переключение версии после контрольного чтения, состояние отказа, сохранение продукта, истории и частных материалов, граница служебных проекций и снимка, отсутствие прежнего источника SoT. Новый инструмент миграции не создаётся.

## Регрессия документации и DocOps

`test_check_workspace.py` проверяет обязательность и корректность Documentation Impact для S1/S2, отсутствие искусственного требования к S0, обновление ссылочных потребителей при MOVE, сохранение принятого свидетельства при разрешённом изменении только ссылок и сохранение исторического исходного пути при разделении документа. Отрицательный случай подтверждает, что некорректное выбранное решение отклоняется, а несвязанный исторический блок не подменяет текущие полномочия.

`test_harness.py` проверяет граф README и документации, непосредственные индексы, ссылки и якоря и только утверждённые устаревшие формы из глоссария. В граф входят README и все поставляемые темы `docs/`; SOP, формы, роли и внутренние создаваемые артефакты не считаются потерянными пользовательскими темами. Отрицательные заготовки проверяют сломанный якорь, потерянную тему, устаревший заголовок SoT и допустимые фрагменты кода и цитат. Навигация Project Start и отсутствие удалённых путей проверяются в действительно созданном Workspace. Ясность и полнота смысла остаются предметом чтения человеком.
