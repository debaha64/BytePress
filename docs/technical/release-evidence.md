# Свидетельства выпуска

Этот документ задаёт спецификацию предварительной проверки выпуска и свидетельств, достаточных для проверки его результата. Порядок действий принадлежит [release-management](../../sops/release-management.md), виды решений и передача полномочий между фазами — [phase-gates](phase-gates.md).

## Как читать документ

- [Основные понятия](#основные-понятия) объясняют различие между наблюдением, техническим выводом и разрешением.
- [Требования](#требования), [инварианты](#инварианты) и [сценарии](#сценарии-и-критерии-проверки) задают проверяемое поведение.
- [Устройство проверки](#устройство-проверки) описывает входы, наблюдаемые данные и ограничения реализации.
- [Проверка конкретного PR](#конкретный-pr-и-наблюдаемые-рецензии) уточняет, какие утверждения можно подтвердить через API.
- [Равенство при переносе](#равенство-при-переносе) определяет свойства, доступные каждому формату.
- [Свидетельства и состояния](#свидетельства-и-границы-состояния) отделяют результат проверки от приёмки и публикации.

## Основные понятия

**Наблюдение** — сведения, заново полученные из GitHub для конкретного репозитория и точки контроля. Сохранённый ответ описывает прошлое состояние; его контрольная сумма подтверждает содержимое записи, но не актуальность правил или полномочий.

**Предварительная проверка** (`preflight`) сопоставляет наблюдаемые факты с ожидаемым состоянием. **Контрольное чтение** (`readback`) независимо наблюдает результат уже выполненного действия и сравнивает его с разрешённой разницей. Эти операции сами ничего не изменяют.

**Цепочка участников** связывает автора изменения, последнего отправителя проверяемого изменения, утверждающих, исполнителя слияния и публикатора. Возможность подобрать участников для маршрута (`potential-route-only`) ещё не доказывает готовность конкретного PR (`exact-pr-gate`).

**Сверка человеком** дополняет факты, которые недоступны автоматической проверке. Результат `OWNER_ACTION_REQUIRED` явно сохраняет эту границу. Сверка не меняет автоматический вывод на PASS и не заменяет решение владельца.

Инструмент не является средством управления выпуском: он не выбирает маршрут, не пишет локальное или внешнее состояние и не выдаёт разрешения.

## Требования

1. `REQ-REL-001`: `preflight` получает новое наблюдение через GitHub API GET для одного точного ID и полного имени репозитория и одной точки контроля. Проверяет ожидаемого участника, видимость, архивный статус, ветвь по умолчанию, точные ссылки, настройки слияния, все наборы правил репозитория и родительских уровней, а также права объявленных участников.
2. `REQ-REL-002`: доказанная цепочка участников без обхода правил проверяет прямой PR из исходной ветви в целевую либо условную рабочую ветвь по выпускной процедуре. В неё входят автор PR, последний отправитель проверяемого изменения, достаточное число отдельных утверждающих, исполнитель с разрешённым способом слияния и публикатор. Одного `push=true` недостаточно. Невыполнимый или неизвестный шаг не даёт PASS.
3. `REQ-REL-003`: `bypass_actors: []` отличается от отсутствующего поля. Отсутствие поля или недостаточные права означают `UNKNOWN` и автоматический `OWNER_ACTION_REQUIRED`. Ответ `404` от API защиты означает `UNKNOWN`, а не `ABSENT`. Отдельное `OWNER_ADMIN_WEB_POLICY_OBSERVATION` может завершить сверку человеком для конкретной точки контроля при явной привязке к источнику, дате, наблюдателю, репозиторию и набору правил. Автоматический вывод остаётся `OWNER_ACTION_REQUIRED`; наблюдение API не переписывается.
4. `REQ-REL-004`: каноническая машинная запись хранит версию схемы, время наблюдения UTC, точные сведения о репозитории, участнике, ссылках, настройках, правилах и правах, контракт точки контроля и компактные объекты. Отсортированный JSON в UTF-8 с единственным завершающим LF и его SHA-256 воспроизводимы для одинаковых нормализованных входов. Время явно исключается только из сравнения без изменений, но не из контрольной суммы свидетельства.
5. `REQ-REL-005`: `readback` независимо читает состояние после действия и сравнивает зафиксированное исходное наблюдение, точную ожидаемую внешнюю разницу и последующее наблюдение. Проверяет весь наблюдаемый состав объектов, настройки, правила, права, точного участника, способ действия и идентичность. Неожиданная разница, отсутствие результата или частичная запись дают FAIL; повторная запись не выполняется.
6. `REQ-REL-006`: сравнение выпускного результата всегда объявляет способ переноса и проверяемые свойства по принятой матрице ниже. Контрольная сумма внешнего файла не доказывает содержимое архива.
7. `REQ-REL-007`: Снимок Workspace, кандидат на приёмку, Product Acceptance, Release Authorization, публикация и контрольное чтение являются разными фактами со своими владельцами; автоматического повышения состояния нет.
8. `REQ-REL-008`: вывод для владельца ограничен вердиктом, объектом действия, идентичностью кандидата или ссылки, выполнимостью цепочки участников, существенными препятствиями и требуемым действием владельца. Инженерный вывод добавляет сводку ссылок и правил и контрольную сумму; машинный вывод доступен только при явном выборе.
9. `REQ-REL-009`: единственный инструмент `tools/release_preflight.py` имеет только `preflight` и `readback`. Project Start поставляет его и тесты, но не запускает. Универсальные проверяющие инструменты остаются без сети и успешно проверяют свежий `sot_files` без GitHub.

## Инварианты

1. `INV-REL-001`: сохранённое свидетельство не является текущим внешним разрешением; контрольная сумма не создаёт полномочия.
2. `INV-REL-002`: PASS предварительной проверки не разрешает `push/PR/merge/tag/release` и не означает Product Acceptance или Release Authorization.
3. `INV-REL-003`: допустимы только явно перечисленные запросы GitHub API GET через массив аргументов с `shell=False`, положительным конечным временем ожидания, перехваченным выводом и закрытым стандартным вводом. Произвольные адреса API, методы и серверы запрещены.
4. `INV-REL-004`: токены, данные доступа, полное окружение и необработанные тела ошибок не попадают в свидетельства или отчёты. Поля с секретами и известные формы токенов или данных доступа отклоняются; stdout/stderr дочернего процесса не пересылаются. Случайное совпадение метаданных со значением не связанной с ними секретной переменной окружения не доказывает утечку и не меняет канонический вывод или его контрольную сумму.
5. `INV-REL-005`: неизвестное блокирующее правило или параметр, неподдерживаемая цель или шаблон правила, противоречие правил и неполное перечисление объектов не дают положительного результата.
6. `INV-REL-006`: новое проверяемое изменение, смена цели, текущего коммита, репозитория, участника, прав, настроек или набора правил делают прежнее свидетельство точки контроля и затронутое разрешение недействительными. Утверждения прежнего коммита недостаточно даже при `dismiss_stale_reviews_on_push=false`.
7. `INV-REL-007`: право обхода правил никогда автоматически не становится обычным разрешённым путём. Непустой список обхода требует отдельного рассмотрения; инструмент обход не выполняет.
8. `INV-REL-008`: `readback` не принимает код возврата записи за свидетельство, не повторяет запись и не обещает отсутствия кратковременных или ненаблюдаемых внешних изменений между двумя чтениями.
9. `INV-REL-009`: обычный снимок задачи после постоянных изменений не имеет сопроводительного файла контрольной суммы. Кандидат на приёмку хранит контрольную сумму, а публичный выпускной файл имеет отдельный контракт контрольной суммы и сопроводительного файла.

Validation, принятие реализации владельцем, Product Acceptance и Release Authorization имеют отдельные точки контроля.

## Устройство проверки

`release_preflight.py` использует только стандартную библиотеку и небольшие чистые функции для нормализации и проверки наблюдений, оценки выполнимости, вычисления канонической контрольной суммы, формирования отчёта, контрольного чтения и сравнения переносимых результатов. Единственный ограниченный адаптер GET использует установленный `gh`. Новых пакетов, сервисов, платформ, настроек или способов аутентификации нет. Импорт не читает сеть и не выполняет команды. Вывод идёт только в stdout; вызывающая сторона сохраняет свидетельства в разрешённом маршруте.

### Вход и защита данных

`preflight --contract <json> [--human-policy <json>] --format owner|engineering|machine` получает новое внешнее наблюдение. Контракт явно задаёт репозиторий, ожидаемые ссылки, правила и настройки, аутентифицированного участника, кандидата и запланированную цепочку участников. Контракт задаёт ожидание, а не разрешение. Полный ответ API не сохраняется: остаются только перечисленные необходимые поля.

Защита секретов опирается на происхождение и структуру данных. Окружение передаётся только дочернему процессу для аутентификации; объект окружения не является свидетельством. Ответ API нормализуется по разрешённым полям. Отклонённый ввод CLI и необработанные тела ошибок не повторяются в выводе. Запрещены поля с секретами, включая составные имена с TOKEN/SECRET/PASSWORD/CREDENTIAL/PRIVATE_KEY, и известные формы `gh*`, `github_pat_*` и Bearer. Значения произвольных переменных окружения не читаются для сравнения со свидетельством; отдельной платформы сканирования или оценки энтропии нет.

### Цепочка участников и состав наблюдения

Контракт цепочки использует существующие ссылки без нового режима маршрута:

1. `source_ref == working_ref` при `source_ref != base_ref`: допустим прямой PR из точно зафиксированной исходной ветви в целевую. Правило PR для зафиксированной исходной ветви не требует новой отправки изменений в этой цепочке; правила целевой ветви, участники, права и способ слияния проверяются как прежде.
2. `working_ref != source_ref` и `working_ref != base_ref`: допустима условная ветвь. Существующая ссылка обязана совпадать с зафиксированным исходным кандидатом; изменение блокирует цепочку. Отсутствующая ссылка позволяет оценить потенциальную выполнимость, но не разрешает создание ветви.
3. `source_ref == base_ref` либо `working_ref == base_ref`: цепочка блокируется.

Оценка цепочки всегда имеет область `potential-route-only`; общий `preflight` получает `exact-pr-gate` только при выборе конкретного PR. Инструмент не выбирает маршрут выпуска, не создаёт ветвь и не выполняет запись. Сверка человеком не является разрешением. Условия и причины применения выпускной ветви принадлежат выпускной процедуре.

Наблюдение включает все ветви и теги, только номера открытых PR, метаданные и рецензии одного выбранного PR, выпуски и их файлы, наборы правил с родительскими уровнями и права перечисленных участников. Подробности и рецензии посторонних PR не запрашиваются. Списки читаются постранично с ограниченным максимумом; неполный или неподдерживаемый ответ не даёт PASS. Сохранённые параметры правил сравниваются точно; неизвестные поля не превращаются в разрешение.

### Контрольное чтение

`readback --contract <json> --before <machine-evidence> --delta <json> --format ...` независимо вызывает тот же адаптер GET. Ожидаемая разница содержит контрольную сумму исходного наблюдения, точку контроля, действие, участника и точные состояния до и после для названных объектов; новые и удалённые объекты также перечислены. Время наблюдения не считается внешним изменением. Любая другая разница наблюдаемого состояния даёт FAIL. Сравнивается всё полученное состояние; непрозрачность правил даёт `OWNER_ACTION_REQUIRED` даже при равенстве наблюдаемых данных.

При слиянии сначала повторно проверяется привязка конкретного PR к зафиксированному исходному наблюдению. Другой PR или исходное состояние без привязки дают FAIL независимо от результата предварительной проверки. Последующее состояние сохраняет идентичность PR, текущий коммит, автора и целевую ветвь. Изменение списка открытых PR допустимо только для точно названного перехода PR.

Независимо наблюдаемые `merged_by`, `merge_commit_sha` и родители Git-коммита доказывают участника и метод `merge`, только если два родителя равны точным исходным коммитам целевой и рабочей ветвей. Состояние REST PR само по себе не доказывает `squash/rebase`: неподдерживаемый точный метод получает `OWNER_ACTION_REQUIRED`. Для Release независимо наблюдаемые автор, ID, тег и файлы дают идентичность и участника. Участник, создавший легковесный тег или отправивший изменения ветви, не выводится из автора коммита или тега.

Если API не даёт независимого факта об участнике, `readback` явно сохраняет частичное наблюдение и `OWNER_ACTION_REQUIRED`. Отсутствующие факты не заполняются из ожидаемой разницы. Для остальных действий точек контроля контракт требует отдельных независимых свидетельств события или аудита по выпускной процедуре; текущий инструмент не создаёт ложный PASS.

Разница `observe` с пустым набором изменений предназначена только для сравнения без изменений. Она не доказывает успех записи. Для любого действия записи пустой набор или отсутствие фактического изменения отклоняются.

### Наблюдение правил человеком

Вход содержит `source=owner-admin-github-web-settings`, дату, наблюдателя, точку контроля, идентичность репозитория, точные ID, имя, цель и режим применения набора правил, списки обхода и состояние классической защиты. Наблюдатель должен совпадать с текущей учётной записью администратора среди объявленных участников. Срок применения ограничен конкретной точкой контроля и датой наблюдения. Ввод человека никогда не делает автоматический вывод положительным. Новая точка контроля требует нового наблюдения владельца или администратора, включая поля правил, скрытые от участника API.

## Конкретный PR и наблюдаемые рецензии

Этот раздел уточняет `REQ-REL-002`, `INV-REL-006` и `SCN-REL-003/008/009` без новой операции или владельца смысла.

1. Пустой `contract.pr_numbers` задаёт `scope=potential-route-only` и `exact_pr_gate.verdict=NOT_YET_OBSERVED`. Даже при PASS цепочки готовность конкретного PR не доказана; `write_authorized=false`. Состав открытых PR хранит только номера. Процедура передаёт выбор через `pr_numbers`; инструмент его не делает.
2. `pr_numbers=[N]` задаёт `scope=exact-pr-gate`. Повторные или несколько номеров, отсутствие выбранного объекта, лишние подробные данные PR или несовпадение ключа и номера дают FAIL. Подробные данные невыбранного PR не игнорируются: требуется исправить выбор.
3. `pr_binding=PASS` требует один наблюдаемый PR: `state=open`, `draft=false`, `merged=false`, `merged_by=null`. Идентичность автора совпадает с ожидаемым автором и участником, чьи права наблюдались; репозитории исходной и целевой ветвей совпадают с точными ID и именем репозитория. Исходная ссылка равна `working_ref`, то есть прямой исходной или условной ветви; её SHA равен зафиксированному кандидату и текущей наблюдаемой рабочей ссылке. Целевая ссылка и SHA равны ожидаемой целевой ветви и текущему наблюдению ссылки. Отсутствующая ветвь или ответвлённый репозиторий (fork) с тем же именем ветви не заменяют точный маршрут.
4. Чтение выполняет GET `/repos/{owner}/{repo}/pulls/{N}` и постраничный GET `/repos/{owner}/{repo}/pulls/{N}/reviews`, затем повторно читает тот же PR. Изменение нормализованного PR во время чтения рецензий даёт FAIL. Перечень разрешённых адресов API дополнен только рецензиями; необработанная история событий, комментарии, GraphQL и запись отсутствуют. API рецензий сохраняет только `id`, `user login/id/type`, `state`, `commit_id`, `submitted_at`; тело, ссылки и необработанный ответ не сохраняются.
5. Утверждение учитывается только для точного текущего SHA и состояния `APPROVED`, если его дал объявленный отдельный утверждающий с текущими правами `write/maintain/admin` и совпадающими `login/id/type`. Последнее по времени окончательное решение участника учитывается один раз. Более позднее `CHANGES_REQUESTED` или `DISMISSED` отменяет утверждение; `COMMENTED/PENDING` его не создаёт. Нераспознаваемые состояние, идентичность, порядок или коммит дают `OWNER_ACTION_REQUIRED`. Недостаточное число утверждений, прежний коммит или неразрешённое требование изменений также не дают PASS.
6. REST `mergeable=true` доказывает только отсутствие обнаруженного конфликта слияния; `false` даёт FAIL, `null` или отсутствие значения — `OWNER_ACTION_REQUIRED`. Это не доказательство выполнения правил рецензирования, установления последнего отправителя, закрытия обсуждений или прохождения проверок. `mergeable_state` не используется как недокументированный источник правил.
7. `require_last_push_approval=true` всегда требует дополнительного независимого доказательства для текущей точки контроля: этот GET-инструмент не получает достоверную идентичность последнего отправителя проверяемого изменения. `last_pusher` из контракта и автор коммита не доказывают отправку. Отдельный утверждающий текущего коммита сам по себе не закрывает требование: автоматический результат — `OWNER_ACTION_REQUIRED`. Аналогично закрытие обсуждений, проверка CODEOWNERS или назначенных рецензентов и неподдерживаемые правила статуса не дают положительного результата. Отсутствующее доказательство явно указано; неподдерживаемая семантика GitHub не подменяется приближением.
8. Для такой точки контроля допустима отдельная сверка владельцем или администратором через веб-интерфейс с источником, датой, наблюдателем, точными репозиторием, PR, исходным коммитом, целевой ветвью, правилами и наблюдаемым состоянием требования. `--human-policy` содержит только сведения о правилах и не закрывает проверку рецензий PR. Инструмент не принимает синтетическое доказательство последнего отправителя. Результат человека не превращается в автоматический PASS и не является Release Authorization.
9. Новая отправка изменений, изменение утверждения, его отмена или требование правок, смена целевой ветви, правил или прав делают затронутое свидетельство недействительным. Перед записью процедура повторяет полное наблюдение. Запросы HTTP не образуют атомарный снимок и не гарантируют отсутствия кратковременного изменения.

Источники фактов — [GitHub PR API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request), [GitHub reviews API](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request) и [правила рецензирования](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). Первый API даёт состояние PR, второй — состояние рецензий. Отдельное состояние разрешения обсуждений недоступно через этот набор REST-запросов; расширение адаптера для него не выполняется.

## Равенство при переносе

Матрица возможностей принята отдельно от конкретного выпуска. Время, UID и GID не являются обязательными свойствами обычного снимка даже для tar, который способен их хранить.

| Способ переноса | Обязательное равенство | Ограничение |
|---|---|---|
| Файловая система / POSIX tar.gz | относительный путь, тип узла, байты файла, POSIX-режимы файлов и каталогов | безопасный единственный корень, без повторных и небезопасных путей; символические и жёсткие ссылки, специальные узлы запрещены выбранным контрактом архива |
| ZIP | относительный путь, представимый тип каталога или файла, байты | режимы доступа — только при доказанных атрибутах Unix для каждой записи; UID, GID, время и каталоги без записей не заявляются |
| Git tree | относительный путь, байты и хеш blob, исполняемость 100644/100755 | режимы каталогов, время и владелец отсутствуют; 120000 означает ссылку и отклоняется текущим контрактом выпуска без ссылок |
| Git checkout | файлы, содержимое и исполняемость при объявленных правилах получения рабочей копии; метаданные корневого .git исключены без чтения | фильтры платформы и конфигурации могут менять байты; рабочая копия сама по себе не доказывает идентичность Git tree |
| GitHub Release asset | точные имя и размер, загруженные байты и SHA-256 | внутренний архив проверяется отдельным разбором по формату; контрольная сумма API не заменяет загрузку |

Несовпадение способа переноса даёт FAIL; неподдерживаемые свойства не игнорируются молча. Инструмент изучает архив без извлечения содержимого и записи файлов. Сравнение публичного файла требует загруженный файл и ожидаемую контрольную сумму, затем проверяет объявленное содержимое tar/ZIP. Эти функции не являются третьей операцией CLI.

## Свидетельства и границы состояния

| Факт | Свидетельство / решение |
|---|---|
| Снимок Workspace | внутренняя передача результата задачи после постоянных изменений; без сопроводительного файла контрольной суммы; контрольная сумма в отчёте владельцу |
| Кандидат на приёмку | точная идентичность и контрольная сумма, способ переноса и технические свидетельства |
| Product Acceptance | отдельное принятое PA-* в соответствующих границах; технический PASS не принимает кандидата |
| Release Authorization | отдельное явное решение владельца для точного действия, объекта, кандидата и текущих правил |
| Публикация | фактическая внешняя запись по разрешению |
| Контрольное чтение | независимое наблюдение результата; FAIL или частичный результат не инициируют повтор |

Машинное свидетельство содержит наблюдение, ожидаемый контракт точки контроля, находки, автоматический вывод, отдельную сверку человеком, выполнимость цепочки участников, контрольную сумму свидетельства и `external_writes=0`. Контрольная сумма подтверждает байты свидетельства, а не происхождение решения владельца. Входные свидетельства считаются доверенными данными владельца или вызывающей стороны, а ответ API — недоверенными внешними данными; ни те ни другие не могут добавлять команды.

Краткий вывод владельцу не содержит необработанный JSON API, строки манифеста или длинные перечни хешей. Инженерное представление включает относящиеся к задаче ссылки, настройки, правила, цепочку участников, препятствия и контрольную сумму наблюдения. Полный машинный документ выводится только при явном `--format machine`.

## Нормативные API источники

Поля API и правила рецензирования сверяются с [GitHub repository rules REST](https://docs.github.com/en/rest/repos/rules), [branch protection REST](https://docs.github.com/en/rest/branches/branch-protection) и [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). Отсутствие поля обхода в API и ответ 404 классической защиты не доказывают отсутствия правил.
