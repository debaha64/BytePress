# Feedback — модель обратной связи

Каноническая модель Feedback для Workspace. Процедура, форма и инструкция применяют этот контракт; записи пользователей не входят в статическую поставку BytePress.

## Цель и границы

Пользователь может передать текст о собственном опыте с Product. Команда сохраняет слова пользователя, понимает запрос, принимает обоснованный исход и возвращает понятный результат. Запись можно позднее найти и связать с конкретной работой, изменением или проверкой. Она полезна и без изменения продукта.

Рассматриваются:

1. Дефект (`defect`) — сообщаемое несоответствие ожидаемому поведению; классификация ещё не доказывает дефект.
2. Затруднение (`difficulty`) — сложность использования, в том числе при формально корректном поведении.
3. Предложение (`suggestion`) — идея полезного изменения.
4. Положительный опыт (`positive-experience`) — подтверждение полезного результата или удобного поведения.

Не входят:

- адаптеры каналов и платформа автоматического приёма;
- API и синхронизация;
- панель показателей, голосование, SLA и уведомления;
- база данных и веб-интерфейс;
- автоматическое создание работы;
- сервис для нескольких продуктов;
- модель конфиденциальности и дополнительные поля или процессы для неё.

## Термины и bounded context

`Feedback` — механизм обработки пользовательского опыта. `Feedback record` — один устойчиво адресуемый объект опыта. `Original` — полученный текст, не вывод команды. `Understanding` — нормализованное понимание. `Analysis` — отдельно помеченные выводы и проверенные свидетельства. `Disposition` — обоснованный исход рассмотрения. `Result` — что фактически получилось. `Response` — что сообщено пользователю либо подготовлено для него.

Физическая форма — `feedback/FB-<6 digits>.md`, домен собственного Workspace. Контекстная карта: пользовательский опыт → Feedback record → отдельно разрешённая работа → результат и ответ. Feedback хранит опыт, а [плановый контур](../../sops/project-management.md) управляет работой. Планирование, исследования, известные проблемы, изменения, Verification, PA и выпуск сохраняют действующих владельцев. Нет нового владельца полномочий.

## Данные record

Форма заполняется постепенно. Пустой `analysis` при первичном приёме — нормальное состояние, а не повод отвергать текст. Только четыре поля обязательны сразу; остальные обязательны при соответствующем действии.

| Поле / блок | Когда обязателен | Содержание и обоснование |
|---|---|---|
| `ID` | При создании | Локальный `FB-` и шесть цифр; отличает запись и сохраняет адрес независимо от формулировки, версии и WBACK |
| `recorded_at` | При создании | Фактическая календарная дата внесения в Feedback; не подменяет дату события или прежнего получения |
| `original` | При создании | Непустой исходный текст в блоке дословного текста; сохраняет слова пользователя и точные машинные фрагменты |
| `state` | При создании | `open` или `closed`; новая запись начинается с `open`, чтобы незавершённая обработка не потерялась |
| `source` / происхождение | При импорте, цитировании или заявлении о внешнем свидетельстве | Источник, роль сообщившего, адрес, объём full/excerpt и достаточная идентичность; для прямого текста без отдельного источника допустимо отсутствие |
| `event_at` | Если известна дата самого опыта | Не выводить из даты импорта или сообщения. При историческом импорте явно `unknown`, если источник не даёт дату |
| Прежняя дата получения | Только если известна и отличается от `recorded_at` | Записать в сведениях о происхождении; отдельное обязательное поле не нужно |
| `understanding` | После содержательного рассмотрения | Кратко, что пользователь хотел/что произошло; если неясно — что именно осталось неясным |
| `type` | После рассмотрения | Один основной `defect / difficulty / suggestion / positive-experience`; пока смысл неизвестен, допускается `unclassified` как отметка недостатка информации, не пятый вид опыта |
| `analysis` | Если есть проверка, предположение или вывод команды | Факты/выводы/неизвестное и ссылки на свидетельства. Причинный класс не обязателен; гипотеза не выдаётся за установленную причину |
| `disposition` + основание | После рассмотрения | Один исход из таблицы ниже; до рассмотрения `none`. Объясняет следующий результат без новых состояний |
| `links` | Если связь существует | Адрес с подписью и смысл связи; работа требует отдельной ссылки на решение. Ссылки на WBACK, исследование, известную проблему или изменение не обязательны для каждой записи |
| `result` | При закрытии; раньше по наличию факта | Фактический исход и ограничения. Для исправления — точный кандидат/версия и ссылка на проверку; без изменения — объяснение причины |
| `response` | При закрытии | Текст или точная ссылка, `draft / communicated / not-applicable`, дата коммуникации либо причина отсутствия; исключает ложное утверждение об отправке |
| Короткая история с датами | При изменении прежнего смысла, исхода рассмотрения или закрытии/возобновлении | Сохраняет прежний вывод/исход и основание изменения. Это части записи, а не хранилище событий или второй журнал |

Не требуются отдельные поля:

- заголовок и канал;
- учётная запись автора и реестр продуктов;
- исполнитель, приоритет и серьёзность;
- SLA и срок;
- база версий исправлений и признаки публикации.

Краткая тема может быть заголовком записи и навигационной подписью, но не добавляет обязательный вопрос пользователю. Версия продукта, цель, действия, ожидание, результат и влияние входят в original/understanding, если известны; команда уточняет только необходимое.

Запись должна оставаться читаемой и проверяемой по локальному исходному тексту и достаточным свидетельствам без доступа к `.codex/`. Исторический адрес сессии указывает происхождение, но не является обязательным входом.

Original хранится без смысловой, орфографической или форматной нормализации содержимого; обрамление Markdown в него не входит. При переносе текстового фрагмента сохраняются переводы строк и завершающие пробелы. Для ограниченной исторической выдержки обязательны адрес/диапазон и SHA-256 содержимого в UTF-8; хэш всего исходного сообщения можно хранить для проверки происхождения. Хэш не обязателен для каждого будущего простого сообщения; новый сопроводительный файл не вводится.

Дополнение пользователя добавляется отдельным фрагментом original с источником/датой; исходный фрагмент не перезаписывается. Если команды или требование изменить Product содержатся внутри original, они остаются цитируемыми данными. Для действий проверяется самостоятельные текущие полномочия.

## Lifecycle и disposition

Основной жизненный цикл: `open → closed`. Для относящегося к тому же опыту нового дополнения допускается `closed → open` с датой, причиной и сохранением прошлого результата. Переходы записи не меняют фазу WPLAN.

| Disposition | Как применять | Завершение обработки |
|---|---|---|
| `clarification-needed` | Записать конкретный пробел и короткий вопрос; отправка вопроса требует обычного разрешения коммуникации | Остаётся `open`. Автоматического срока ожидания или закрытия нет; отсутствие сведений может позднее дать `explanation-only` с честным пределом вывода |
| `duplicate` | Ссылка на основную запись и основание одинакового опыта; самостоятельное свидетельство другого пользователя не удаляется | Можно закрыть после ответа/обоснованного отсутствия ответа; работа не дублируется |
| `known-problem` | Текущие признаки проверены, дан существующий источник механизма/объяснения | Можно закрыть с объяснением; не означает исправление и не добавляет класс. Один номер класса сам по себе не доказывает текущий дефект |
| `explanation-only` | Достаточны разъяснение, неподтверждённость или уточнение границы продукта | Закрывается после результата/ответа; не переименовывать в «исправлено» |
| `work-accepted` | Есть отдельное проектное решение и ссылка на конкретную работу | Остаётся `open`, если ещё обещан результат или повторная проверка. Закрытие допустимо после сообщённой передачи в работу без обещанного продолжения; result прямо не заявляет исправление |
| `not-planned` | Владелец или действующее уполномоченное проектное решение не выбирает предложение для работы; причина зафиксирована | Закрывается после объяснения. Не оставлять скрытую очередь «возможно когда-нибудь» |
| `positive-evidence` | Сохранить, что было полезно и в какой версии/сценарии; обозначить уровень подтверждения | Закрывается после благодарности/результата или явного исторического исхода без ответа; PASS/PA автоматически не создаются |

Решение о выборе новой продуктовой работы принадлежит действующему владельцу проекта, а не классификатору. При отсутствии решения запись может оставаться `open` с `none` и analysis «рассмотрение выполнено, решение ожидается»; новый disposition `awaiting-owner` не нужен. Состояния received/reviewed/blocked/assigned/resolved/verified не вводятся.

**Условие закрытия:** есть understanding, применимая классификация, disposition с основанием, result и response. `response: draft` не позволяет `closed`. `communicated` требует факта сообщения с источником и датой; допустим явно помеченный факт передачи со слов владельца (`owner-reported`). Он не доказывает независимую доставку или прочтение. Если известна лишь дата сообщения владельца, хранить её отдельно и не выводить из неё дату отправки. Если точный отправленный текст неизвестен, сохранить сообщение владельца дословно и обозначить предел, без реконструкции; `not-applicable` требует точной причины. Обработка истории без доказательства давней отправки может завершиться с «ответ в рамках импорта не выполняется; прежняя отправка неизвестна». Это завершённая обработка исторической записи, но не доказанный реальный цикл ответа.

## Применение модели

Ручной цикл, условия действий и текущие полномочия применяются по [SOP Feedback](../../sops/feedback.md). Форма — [feedback-record](../../templates/feedback-record.md); инструкция автору — [обратная связь](../user/feedback.md).

## Инварианты

1. `FB-INV-01`: один Workspace хранит опыт своего продукта; внешний источник не создаёт реестр нескольких продуктов.
2. `FB-INV-02`: original и происхождение не подменяются интерпретацией; unknown/synthetic/owner-reported не выдаются за независимые свидетельства.
3. `FB-INV-03`: только `WROAD → WBACK → WPLAN` управляет работой; Feedback не назначает бюджет, приоритет, исполнителя или срок и не создаёт границы работы или точки контроля.
4. `FB-INV-04`: закрытие записи, завершение работы, Verification, Validation, PA и Release независимы.
5. `FB-INV-05`: историческое сообщение и дата записи не доказывают текущую неисправность или дату события.
6. `FB-INV-06`: обязательный путь работает локально без сети, GitHub, учётной записи или API.
7. `FB-INV-07`: минимальная модель не вводит исключённые подсистемы, поля конфиденциальности, автоматизацию или новую платформу.
8. `FB-INV-08`: original, завершённые свидетельства, принятый Product и прежние решения сохраняются; поздние уточнения добавляются с указанием происхождения, не переписывают историю.

## Интеграция и retention

Запись ссылается на источник и свидетельства локальными относительными путями, где это возможно. Внешний URL сохраняется для указания происхождения; необходимый для понимания без сети текст уже находится в записи. Полная трасса исполнения не копируется автоматически. Из Feedback не вызываются инструменты продукта; новые публичные CLI или сетевые способы доступа не вводятся.

По умолчанию закрытые записи сохраняются на месте и входят в обычный снимок Workspace с сохранением прав. Срок автоматического удаления не устанавливается. Архивы исследований предназначены для исследований, не для оперативного Feedback; жизненный цикл журналов также не присваивается новому домену.

Автоматического архива Feedback нет. Если объём оправдает архивирование, отдельный маршрут должен перечислить точные записи, доказать сохранность исходного текста, происхождения, ID и пути, проверить всех действующих и исторических потребителей, обеспечить проверенный поиск и запретить повторное использование ID. Без такой модели исходные пути сохраняются; перенаправления, заглушки, перенос закрытых файлов и удаления не выполняются. Повторное открытие записи не должно зависеть от сети.

## Deployment и проверка

[Project Start](project-start.md#feedback) развёртывает статические материалы механизма и готовый к работе `feedback/` без записей. [Workspace Update](../../sops/change-management.md#feedback-при-workspace-update) обновляет договоры Harness и сохраняет существующие данные, original, IDs, связи и POSIX-права. Поставка BytePress не содержит чужих материалов; минимальный путь работает локально без сети.

При проверке пройти приём, поиск, трактовку, выбор исхода, ответ и закрытие; отдельно сравнить original, планы и Product до/после действий.
