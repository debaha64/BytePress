# Подготовка репозитория GitHub

Эта инструкция помогает владельцу или администратору подготовить репозиторий для `sot_github`. В этом режиме принятая базовая версия находится в ветви по умолчанию ожидаемого репозитория GitHub, а локальный Git служит рабочей копией. Настройка репозитория сама по себе не разрешает публикацию изменений или выпуск.

## Выберите участников

Определите, кто создаёт изменения, кто их утверждает, кто выполняет слияние и кто публикует выпуск. BytePress не создаёт учётные записи и не управляет правами доступа.

| Профиль | Что решить и проверить |
|---|---|
| Одна учётная запись | Совмещение ролей допустимо, только если действующие правила не требуют независимого утверждения. Запись решения владельца не заменяет обязательную проверку GitHub. |
| Владелец и агент | Можно выделить агенту отдельную учётную запись, а владельцу оставить утверждение конкретного коммита. Это рекомендуемый профиль, но отдельная учётная запись агента не обязательна. |
| Команда | Определите права участников, необходимое число утверждений и применимость CODEOWNERS по правилам репозитория. |

Выдайте минимальные необходимые права. Не предоставляйте обход правил как обычный способ работы. Если правила требуют утверждения последнего изменения другим участником, убедитесь, что такой участник доступен и имеет нужные права.

## Выберите ветви

- Минимальный профиль: одна ветвь по умолчанию и короткоживущие рабочие ветви. Подходит для простого продукта и выпуска без отдельной стабильной ветви.
- Выпускной профиль: ветвь разработки по умолчанию и отдельная стабильная ветвь для выпуска. Выбирайте его, когда продукту нужна отдельная выпускная линия; ветви выпуска и срочного исправления используются в соответствующих выпускных маршрутах.

Имена ветвей задаёт ваш репозиторий. `sot_github` не требует `develop/main`; эта пара используется проектом BytePress, но не является общим требованием Harness.

## Настройте репозиторий

1. Если репозиторий уже заполнен, создайте проверяемую резервную копию ветвей, тегов, настроек и метаданных выпусков. Независимо проверьте возможность восстановления.
2. Назначьте участников и права по выбранному профилю.
3. Создайте необходимые ветви и выберите ветвь по умолчанию.
4. Защитите выбранные ветви от прямой отправки изменений, удаления и принудительной перезаписи. Настройте Pull request и обязательное закрытие обсуждений согласно своей политике.
5. Установите число обязательных утверждений. Для одной учётной записи допустимо `0`, если независимая проверка не требуется; при разделении ролей обычно нужно утверждение текущего коммита. Командные правила могут быть строже.
6. Для обычных изменений выберите Squash and merge. Способ слияния выпусков и срочных исправлений задайте отдельно по политике ветви. Обязательные проверки статуса можно настроить по потребностям проекта; текущий базовый контракт BytePress их не требует.
7. Включайте автоматическое удаление рабочей ветви только после проверки выбранного порядка слияния.

Утверждение относится к конкретному текущему SHA коммита. После нового изменения требуется новое утверждение. Выполнить слияние может любой участник с необходимыми правами; он не обязан совпадать с утверждающим. Создание тега и GitHub Release требуют отдельных решений владельца.

## Подготовьте подключение Workspace

Передайте точную идентичность репозитория в форме `owner/repository` и проверьте доступ выбранной учётной записи. Не помещайте токены или другие секреты в документацию проекта.

После разрешённого перехода Project Profile содержит `sot_mode=sot_github`, а `AGENTS.md` — ровно одно поле `SOT_GITHUB_REPOSITORY`. Локальная рабочая копия подключена через единственный `origin` к этому репозиторию. URL, имена ветвей, учётная запись и данные доступа в Project Profile не хранятся.

Подготовку локальной копии и переход режима исполнитель выполняет по [процедуре SoT](../../sops/sot.md). Поддерживаемые URL и точные условия локальной проверки описаны в [технической справке Git](../technical/git.md).

## Если репозиторий уже заполнен

Согласуйте сохранение опубликованной истории. Рабочая ветвь должна исходить из проверенной версии удалённого репозитория; в неё переносят только проверенное содержимое файлов. Независимую локальную историю нельзя присоединять автоматически. Иной порядок с разрушением истории требует отдельного решения владельца.

Переход проходит через два отдельных состояния:

```text
sot_files -> sot_git -> sot_github
```

Обратные переходы текущим контрактом не поддерживаются. [Выбор режима](source-of-truth-mode.md) объясняет различия, а [SOP](../../sops/sot.md) задаёт порядок перехода.

## Как проверить готовность

- В GitHub видны ожидаемый репозиторий, ветвь по умолчанию и защита нужных ветвей.
- Назначенные участники имеют необходимые права; обязательное утверждение может выполнить доступный участник.
- Выбранные способы слияния соответствуют правилам ветвей.
- Исполнитель передал результат подготовки и локальной проверки Workspace без ошибок.

Локальная проверка не подтверждает свежесть настроек GitHub. Перед конкретным внешним действием применяется отдельная [выпускная процедура](../../sops/release-management.md). [Спецификация выпускных свидетельств](../technical/release-evidence.md) объясняет пределы автоматической проверки и случаи, в которых нужны сведения от администратора.
