# Workspace Update

Workspace Update обновляет Harness в существующей рабочей среде. Продукт, идентичность проекта, история и выбранный режим источника истины сохраняются. Project Start предназначен для создания отдельного Workspace.

## Подготовить обновление

- Узнайте текущий `harness_version` в корневом Project Profile и версию новой поставки в `VERSION`.
- Подготовьте проверяемый снимок существующего Workspace.
- Укажите исполнителю, какой Workspace обновить, какую поставку использовать и какие частные изменения нужно сохранить.

Исполнитель запускается из новой проверенной поставки. Обычный Update выполняется без исполнения и активного WPLAN; подготовительный исследовательский WPLAN под старым проверяющим инструментом не открывается. Если разрешённую работу блокирует дефект Harness, допускается узкое [восстановление с сохранением активного WPLAN](../../sops/change-management.md#recovery-при-active-wplan): остановить записи, подготовить точную резервную копию и воспроизводимое свидетельство препятствия, отдельно разрешить точные изменения Harness. Продукт, маршрут, исследования, журналы и Feedback сохраняются; активный WPLAN не закрывается ради обновления. Владелец отдельно разрешает точную резервную копию с хэшем, новую поставку и полный список изменений после анализа различий. Исполнитель обновляет только разрешённые поверхности и проверяет сохранность продукта и истории. Нормативная процедура принадлежит [change-management](../../sops/change-management.md#workspace-update).

## Ожидаемый результат

После проверок Workspace работает с обновлённым Harness; `harness_version` отражает успешно применённую версию. Принадлежащий продукту `VERSION`, продуктовая приёмка и разрешение выпуска имеют отдельные основания.

При отказе обновление не считается завершённым: сохраняются сведения о промежуточном состоянии и прежняя версия Harness; восстановление требует точного плана по подготовленному снимку. Изменения конкретного перехода описаны в [0.5.1 → 0.5.2](migration-0.5.1-to-0.5.2.md).

## 0.5.2 → 0.5.3 Workspace Update

Исправление касается первого исследования, его полномочий и начального состояния архива, создаваемого реестра SYSTEM и команд проверки Harness. Применяется [внешняя граница Update](../../sops/change-management.md#внешняя-граница-workspace-update); для точного обновления существующего Workspace, нужны следующие различия:

1. Сохранить снимок, корень продукта, WROAD/WBACK/WPLAN, историю, исследования и частные изменения; начальный `harness_version` оставить `0.5.2`. Для существующего Profile повторная смена владельца конфигурации не требуется.
2. Создать отдельный эталонный Workspace из поставки `0.5.3`. По фактической разнице двух свежих развёртываний задать действие для каждого изменённого пути; списка COPY недостаточно. По фиксированному копируемому манифесту перенести изменённые проверяющий инструмент и тесты, phase-gates, SOP interview/project-management/research/change-management, формы активного WPLAN и SYSTEM, эту инструкцию. Частные варианты объединить по смыслу, совпадающие копируемые файлы — по точным байтам и правам. Создаваемый docs/technical/project-start.md получает GENERATED_MERGE; создаваемая навигация также проверяется отдельно. Принадлежащий только исходнику new_project.py обновляется в поставке, в развёрнутый Workspace его не переносить.
3. В существующий SYSTEM семантически добавить реестр из созданного эталонного SYSTEM, подставив реальный Slug. Единственный маркер `registry:protected-surfaces` и таблица `Path | Protection` остаются в SYSTEM; существующие более строгие защиты сохраняются. корень продукта защищён до точки контроля реализации. Не заменять SYSTEM, AGENTS, README или планы/историю целиком эталонными файлами.
4. Не создавать архивный слой ради первого исследования. Если имеется преждевременный один archives/README.md, считать его отдельным явно учтённым остатком в точном перечне действий обновления; не удалять исторические архивы или содержимое автоматически.
5. Выполнить контрольное чтение копируемых байтов/прав, проверяющий инструмент, применимые тесты и проверки сохранности при версии `0.5.2`. Начальное состояние проверить на отдельной копии: первое исследование имеет `AUTHORITY_REF: none`, без OD реализации, с непустой рабочей границей и защищённым Product. Старый OD реализации не используется как обход ошибки.
6. Только после успешного контрольного чтения обновить текстовую проекцию версии SYSTEM, если она имеется, и последним переключить `harness_version` через каноническую сериализацию Profile на `0.5.3`; повторить проверки. При отказе оставить прежнюю версию и промежуточные свидетельства.

Частные данные конкретного проекта для этой проверки не требуются: нейтральная заготовка воспроизводит сохранность продукта, истории и WROAD и начальное состояние. Обновление конкретного Workspace выполняется только по отдельному точному разрешению внешней операции. Успешный обычный Update заканчивается дозаписью свидетельств в обновлённом Workspace; первая дальнейшая задача открывает обычный WPLAN. Восстановление передаёт свидетельства вне цели и сохраняет прежний активный WPLAN; его дальнейшая работа выполняется только по обычным полномочиям. В обычной поставке развёрнутого инструмента очистки нет; локальный частный инструмент сохраняет собственный договор. Команды [change-management](../../sops/change-management.md) не требуют инструменты только исходной поставки.

## Сохранение обратной связи

Обновление добавляет [механизм Feedback](feedback.md), если его ещё нет. Ваши существующие `feedback/` записи, исходные тексты и индекс сохраняются вместе с правами доступа. Пустой индекс из эталонного Workspace не заменяет ваш индекс. Исполнитель отдельно проверяет сохранность данных и обновление инструкции, формы и SOP по [контракту Update](../../sops/change-management.md#feedback-при-workspace-update). При одинаковом `harness_version` точную поставку различают по Product manifest и SHA-256, а не по версии.


## 0.5.3 → 0.5.4 Workspace Update

Обновление исправляет проверку фактической дельты при закрытии последнего WPLAN и упрощает его форму. Используйте существующую [процедуру Workspace Update](../../sops/change-management.md#workspace-update). Если доказанный дефект блокирует закрытие единственного активного WPLAN, применим раздел [Recovery](../../sops/change-management.md#recovery-при-active-wplan).

1. Проверьте точные выпущенную 0.5.3 и кандидат 0.5.4, резервную копию и полный перечень действий по двум свежим эталонным развёртываниям. Существующие продукт, проектная документация, исследования, история, Feedback, WROAD/WBACK/WPLAN и частные данные сохраняются.
2. Перенесите только изменившиеся договоры Harness по перечню действий. Создаваемый `docs/technical/project-start.md` требует проверенного объединения; частные владельцы сохраняют проектный смысл и права доступа. `new_project.py` принадлежит только исходной поставке и в развёрнутый Workspace не переносится.
3. Оставьте старый активный WPLAN с его заголовками со счётчиками, ALLOWED_SURFACES и PRESERVE без переписывания во время Update. Новый проверяющий инструмент принимает эту форму; новый шаблон WPLAN использует только CREATE/UPDATE/REMOVE без счётчиков.
4. Выполните контрольное чтение обновлёнными target/tools при прежнем `harness_version`; проверьте байты, типы, права всех сохранённых данных и прежнюю идентичность активного WPLAN. Только после PASS обновите связанную текстовую проекцию версии и последним `harness_version` через каноническую сериализацию на полное значение VERSION новой поставки, затем повторите проверки.
5. Перед отдельно разрешённым закрытием подготовьте закрывающие объявления существующего WPLAN, получите свежую полную исходную базу уже после Update, выполните перенос с тем же ID и фиксацию конечного маршрута. Итоговая проверка — `tools/check_workspace.py --workspace <path> --baseline-manifest <closing-baseline>`. Новый WPLAN и фиктивный переход фазы для закрытия не требуются.

Успешный Update либо повтор на одноразовой копии не означают Product Acceptance, Release Authorization или независимую Validation принимающей команды.


## Предварительная и окончательная поставки

Укажите полное значение VERSION новой поставки по [SOP версий](../../sops/semver.md#развёрнутая-версия). Исполнитель подтвердит его после проверки обновлённого Workspace.

Если номер совпадает, попросите исполнителя сравнить точное содержимое исходных поставок и выполнить [процедуру Update](../../sops/change-management.md#workspace-update). Исторические исключения, включая candidate-1, описаны у [владельца договора](../../sops/semver.md#исторические-исключения).
