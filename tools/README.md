# Инструменты

`tools/` хранит узкие исполняемые возможности BytePress Harness; автоматизированные доказательства находятся в `tests/`.

| Инструмент | Назначение |
|---|---|
| `project_profile.py` | строгий разбор Project Profile по схеме v1, проверка в контексте файловой системы и каноническая сериализация; объявленные команды не исполняет |
| `new_project.py` | Project Start v1: `preview` без записи и `apply` с разрешением по контрольной сумме; фиксированный перечень поставки, соседний промежуточный каталог, только копирование существующего продукта и восстановление через повторный `apply` |
| `check_workspace.py` | универсальная проверка внешнего Workspace, Project Profile, планирования, SoT, файлов Workspace, ссылок, остатков и необязательного состояния жизненного цикла и сохранности; содержимое продукта не сканирует и не исполняет |
| `check_product.py` | универсальная проверка состава продукта, объявленных частей и проверок; по умолчанию проверяет только состав, явное исполнение требует `--run-native-checks --timeout-seconds <N>` |
| `bp_clean.py` | отдельная ограниченная очистка точного набора временных остатков статической Product Unit BytePress; ошибки проверяющего инструмента не исправляет |

Проверяющие инструменты независимы, не вызывают друг друга и используют только размещённый рядом канонический `project_profile.py`. Запуск проверок продукта остаётся внутри `check_product.py`: прямой массив аргументов без оболочки, ограниченные рабочий каталог и исполняемый файл, унаследованное окружение, закрытый стандартный ввод и перехваченный вывод. Превышение времени ожидания, прерывание или изменение контекста дают отказ. Третьего квалификационного CLI и обёртки совместимости нет.

## Проверка поставки

Инструменты и тесты продукта не запускаются из защищённого исходника. Порядок проверки принадлежит [verify-work](../sops/verify-work.md). На свежей внешней копии сначала выполняется квалификационный набор, затем настоящий Project Start создаёт внешний Workspace для запуска развёрнутых проверок:

```bash
python3 -B -c 'from pathlib import Path; paths = (Path("tools/check_workspace.py"), Path("tools/check_product.py"), Path("tools/bp_clean.py"), Path("tools/project_profile.py"), Path("tools/new_project.py")); [compile(path.read_text(encoding="utf-8"), str(path), "exec") for path in paths]'
python3 -B -m unittest discover -s tests -p 'test_*.py'
python3 -B <external-workspace>/tools/check_workspace.py --workspace <external-workspace>
python3 -B <external-workspace>/tools/check_product.py --workspace <external-workspace>
python3 -B tools/bp_clean.py --repo .
```

Проверки средствами продукта запускаются только отдельной явной командой с положительным временем ожидания. `PYTHONPATH`, рабочий каталог, тесты, исполняемые файлы проверки и очистки и импортированные модули должны быть ограничены одной свежей копией. Проверяющий инструмент не выполняет сеть, запись GitHub, автоматическое исправление или приёмку. Технический PASS не является Product Acceptance.

## Исполнимый SDLC

`check_workspace.py` проверяет компактную запись `SDLC_TRANSITION: v1`, канонические фазу и роль, требуемый вид свидетельства, политику точки решения владельца и точный вид решения из одной строки перехода [phase-gates](../docs/technical/phase-gates.md). Затем сверяет точные типизированные ссылки на полномочия и решение. Скрытого второго соответствия перехода и вида решения, переопределения вида решения именем точки контроля WPLAN и подстановки произвольного положительного решения нет.

`--print-baseline-manifest` без записи выводит полный TSV в stdout до изменений. Необязательный `--baseline-manifest <complete.tsv>` затем сопоставляет точные `CREATE/UPDATE/PRESERVE/REMOVE` WPLAN с фактическими изменениями постоянной файловой области, включая тип, режим доступа и содержимое. Инструмент сам не пишет исходную базу и не выполняет точку решения владельца.

## Выпускные свидетельства

`release_preflight.py` — отдельный инструмент только на чтение:

- `preflight --contract <json>`;
- `readback --contract <json> --before <json> --delta <json>`.

По умолчанию вывод предназначен владельцу; `--format engineering|machine` выбирается явно. `--timeout` требует положительное конечное значение. Коды выхода: `0` — PASS, `1` — FAIL, `2` — OWNER_ACTION_REQUIRED. Ни один код не разрешает запись.

Наблюдение правил владельцем или администратором передаётся в `preflight` через `--human-policy`. Неизвестное состояние API сохраняется; сверка человеком имеет отдельные вывод, источник и дату. [Контракт](../docs/technical/release-evidence.md), [процедура](../sops/release-management.md) и [тесты](../tests/test_release_preflight.py) имеют свои роли.

Project Start поставляет инструмент и тесты, но не запускает их; оба универсальных проверяющих инструмента работают без GitHub. `readback` самостоятельно читает текущее состояние после действия. Если точный участник или метод недоступны API, результат остаётся частичным с `OWNER_ACTION_REQUIRED`, без повтора. Функции сравнения используют объявленные свойства файловой системы, tar, ZIP и рабочей копии Git и отдельно проверяют контрольную сумму загруженного файла выпуска.

## Проверки документации

Существующий инструмент Workspace требует для S1/S2 один непустой Documentation Impact с решением о влиянии, точными путями владельцев смысла и причиной по [change-management](../sops/change-management.md#documentation-impact). Он проверяет структуру, а не полноту выбранного влияния. Граф входа в продуктовую документацию, якоря и утверждённые устаревшие формы проверяет `test_harness.py`. Отдельного исполняемого инструмента документации или точки контроля AI нет.
