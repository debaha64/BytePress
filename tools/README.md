# Инструменты

`tools/` хранит исполняемые рабочие инструменты Product Unit. Автоматизированные технические проверки находятся в `tests/` и не являются инструментами.

Локальные инструменты Product Unit:

- `bp_check.py` выполняет лёгкую проверку текущего состояния Product Unit;
- `bp_clean.py` удаляет exact disposable set только после доказательства корня Product Unit для `--apply`; `.agents/` и `.codex/` обрабатываются только с `--local-service`, а raw и используемые clean evidence сохраняются.

Инструменты не создают и не восстанавливают Harness, не вычисляют следующий маршрут, не управляют Workspace и не выполняют начальную настройку Git.

## Граница проверки

`bp_check.py` проверяет:

1. безопасную границу символических ссылок и локальных путей;
2. наличие обязательных текущих файлов;
3. валидность локальных Markdown-ссылок;
4. от нуля до одного активного PLAN и его минимальные поля;
5. `ALLOWED_SURFACES` и защиту системных файлов;
6. `SOT_MODE` как единственное объявление одного из трёх режимов и условное поле `SOT_GITHUB_REPOSITORY` только при `sot_github`;
7. отсутствие Git-вызовов при `sot_files`;
8. текущий корень репозитория, `HEAD`, чистое дерево и отсутствие удалённого репозитория при `sot_git`;
9. при `sot_github` — подготовленные локальные `origin`, идентичность URL, вышестоящую ветвь, удалённые ссылки, символическую ссылку `origin/HEAD` и допустимое расхождение;
10. отсутствие одноразовых текущих путей по exact disposable contract;
11. идентичность продукта и корневой README с приоритетом продукта;
12. текущие ссылки активного PLAN на IE, решение о реализации и продуктовую приёмку;
13. текущее состояние продукта и фазу активного PLAN;
14. полное каноническое перечисление фаз `01–21`, обязательные `roles/` и минимальную поверхность `skills/`.

Проверка не реконструирует Git-историю, не классифицирует коммиты, не использует сеть и не выполняет автоматическое исправление. Метаданные GitHub, аутентификация, `fetch` и подготовка `origin/HEAD` относятся к внешней предварительной проверке.

## Команды

Канонический запуск тестовых модулей принадлежит [tests/README.md](../tests/README.md); здесь он приведён только как часть полной проверки Harness/tool/test.

```bash
python3 -m py_compile tools/bp_check.py tools/bp_clean.py tests/test_harness.py
python3 -m unittest discover -s tests -p 'test_*.py'
python3 tools/bp_check.py --repo .
python3 tools/bp_clean.py --repo . --apply
python3 tools/bp_check.py --repo .
```

Полный `unittest discover` обязателен для изменения Harness/tool/test. Для обычной работы набор выбирается по затронутому контракту в `sops/verify-work.md`.

В `sot_files` инструменты не читают `.git` и не вызывают Git CLI. В `sot_git` проверяется только текущий локальный корень; удалённый репозиторий и грязное дерево дают `FAIL`. В `sot_github` проверка использует только уже существующие локальные Git-ссылки и никогда не вызывает `fetch`, `pull`, `push`, `gh`, `curl` или `wget`.

## Дефект Harness

При дефекте Harness в `product-work` агент выводит:

```text
HARNESS_BLOCKER: <краткое описание>
```

и прекращает изменения. Исправление не проектируется из `product-work`; режим `system-editing`, начатый владельцем, требует уже принятого решения владельца и активного PLAN.

Технический PASS не создаёт `PA-*` и не является продуктовой приёмкой.
