# Старт сессии

Прочитать `AGENTS.md`, `SYSTEM.md`, активный PLAN, `plans/backlog.md`, `plans/roadmap.md` и относящиеся к задаче SOP.

В стартовой обвязке Product Unit управляющий активный PLAN находится в `plans/active/`.

## Первый старт

Для первого старта существующего контура:

1. Прочитать `README.md`, `AGENTS.md` и `SYSTEM.md`.
2. До любых Git-команд прочитать объявленный режим SoT в `AGENTS.md`.
3. При `sot_git` до интервью обработать вход с существующим или отсутствующим репозиторием по `sops/sot.md`.
4. Для отсутствующего репозитория после первого запроса автоматически создать исходное состояние неизменённой Product Unit; отдельное разрешение владельца не спрашивать.
5. При `sot_github` выполнить внешнюю предварительную проверку идентичности, метаданных, `fetch` и `origin/HEAD`, затем локальную диагностику без сети.
6. Проверить обязательные поверхности командой `python3 tools/bp_check.py --repo .`; отсутствующий обязательный файл даёт `FAIL` и не восстанавливается автоматически.
7. Найти активную `ROAD`, активную `BACK` и единственный активный `PLAN` в управляющем контуре текущей работы.
8. Определить фазу SDLC, точку контроля, `Маршрут решений`, роль, разрешённые файлы и запреты.
9. Проверить, требуется ли решение владельца для ближайшего перехода.
10. Продолжать работу только в границах активного PLAN.
11. Если есть внешний домен-свидетельство, указать его в `Состоянии агента`.

При `sot_files` Git CLI запрещён до отдельного перехода, утверждённого владельцем. Отсутствие `.git` проверяется файловыми средствами.

При `sot_git` без `.git/` инструменты Product Unit не создают репозиторий. Checker запускается после создания исходного состояния, потому что объявленный режим требует локальный repository.

Для первого старта Product Unit:

1. Использовать его собственный `ROAD -> BACK -> PLAN`.
2. Считать первый продуктовый запрос входом стартового исследования (`discovery`) до решения владельца.
3. Не переходить к коду, пока точка контроля после `discovery` не выполнена по `sops/managed-agent-pass.md`.

## Порядок восстановления

Порядок восстановления:

1. `AGENTS.md`;
2. `SYSTEM.md`;
3. `plans/active/`;
4. `plans/backlog.md`;
5. `plans/roadmap.md`;
6. `plans/completed/`;
7. `logs/sessions.md`;
8. `logs/quality.md`;
9. `logs/risks.md`;
10. документы-владельцы смысла.

Сессия не требует отдельного `state/session-handoff.md`, если плановый контур, журналы и чистое завершение (`clean-exit`) актуальны.

Стартовое `Состояние агента` показывает:

1. цель;
2. статус;
3. ROAD/BACK/PLAN;
4. фазу и точку контроля;
5. режим SoT; для `sot_files` — подтверждение полного игнорирования `.git`, для `sot_git` — состояние локального репозитория, для `sot_github` — идентичность репозитория, `origin`, вышестоящая ветвь, `origin/HEAD` и граница внешней предварительной проверки;
6. точку контроля и `Маршрут решений`, если они есть в активном PLAN;
7. запреты;
8. внешний домен как свидетельство, если применимо;
9. следующий шаг.
