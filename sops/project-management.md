# Управление проектом

Workspace ведёт контур `WROAD -> WBACK -> WPLAN` в `WS_<Slug>/plans/`; Product Unit не хранит и не исполняет этот маршрут.

## ID плана

1. WPLAN ID уникален и не переиспользуется.
2. Имя файла и заголовок содержат один ID.
3. Перенос в `plans/completed/` не меняет ID.
4. Префикс `COMPLETED-` запрещён.
5. Новый активный WPLAN получает следующий свободный ID по активным и завершённым WPLAN.

## Активный WPLAN

Новая короткая форма и условия открытия находятся в разделе [Разделение работы и состояния](#разделение-работы-и-состояния). Источник полномочий, точные пути/операции и обязательный результат сохраняются. Существующие старые WPLAN читаются совместимо; phase/role/status projections остаются только в старой форме. Ни форма, ни роль не разрешают запись сами по себе.

## Точка контроля реализации

До реализации Product получить применимые требования, конструкцию и решение в точной границе владельца DECISION_KIND: implementation для текущего WPLAN. Полный явный запрос реализации достаточен, если предмет и необходимые условия уже определены; повторное подтверждение не требуется. Продуктовое интервью собирает только отсутствующие сведения и не создаёт synthetic IE. Точные операции и дополнительные ограничения проверяются независимо. Условия действия принадлежат phase-gates, приёмка и выпуск остаются отдельными решениями.

## Фаза активного WPLAN

Состояние продукта принадлежит его требованиям, архитектуре, решениям и выпускным свидетельствам. WPLAN хранит разрешённую работу, а сессия — только отрезок исполнения. Каталог SDLC помогает выбрать нужные инженерные этапы; роль и название этапа не создают полномочий.

## Продуктовая приёмка

По прямому запросу подготовить точный результат к рассмотрению. Accepted PA записывается только по явному решению владельца; release readiness потребляет существующий PA с сохранением происхождения и проверкой exact candidate. [Условия действий](../docs/technical/phase-gates.md#условия-действий) не объединяют PA с разрешением выпуска.

## Защищённые поверхности

Канонический реестр находится в `SYSTEM.md`. В `product-work` защищённые поверхности запрещены, кроме точных исключений `<Slug>.profile:sot_mode` и `AGENTS.md::SOT_GITHUB_REPOSITORY`, уже разрешённых владельцем и WPLAN для одной контрольной отметки перехода.

При запрещённом изменении или дефекте Harness агент выводит:

```text
HARNESS_BLOCKER: <краткое описание>
```

и прекращает изменения. Агент не проектирует исправление, не запрашивает `system-editing WPLAN`, не предлагает повторное исполнение, не создаёт исследование Harness и не управляет Workspace.

## SoT и локальная Git-работа

Project Profile `sot_mode=sot_git` сам по себе разрешает только начальную настройку отсутствующего неизменённого репозитория. Переход режима и `local_git_route` являются разными решениями владельца. Для одного WBACK существует не более одного `local_git_route`; WPLAN сужает его через CREATE ∪ UPDATE ∪ REMOVE.

Проверку режима и разрешённые действия выполнить по [SoT](sot.md); точные условия локального состояния принадлежат [справке Git](../docs/technical/git.md). Управление проектом не вводит вторую процедуру подготовки репозитория.

Для `S1/S2` кратко зафиксировать в WPLAN класс, владельца спецификации и применимые `REQ/INV/SCN`; для `S2` — также точный анализ влияния и набор изменений, прослеживаемость, уровень свидетельств и Consistency Closure. Полную спецификацию WPLAN не копирует. Порядок работы: основные действия → Bugfixes → Consistency Closure → проверка и контрольное чтение → точка решения владельца.

## Исполнение перехода фазы

Новая форма использует [условия действий](../docs/technical/phase-gates.md#условия-действий). Сохранённые старые WPLAN проверяются по прежнему SDLC_TRANSITION; его граф не является обязательным для новых работ.

## Передача выпускных свидетельств

[Выпускная процедура](release-management.md) владеет предварительной проверкой текущего внешнего состояния, оценкой цепочки участников и независимым контрольным чтением. [Спецификация свидетельств](../docs/technical/release-evidence.md) разделяет снимок, кандидата, Product Acceptance, Release Authorization и публикацию. Полномочия фаз и решений задаёт phase-gates. Предварительная проверка никогда не повышает состояние автоматически.

## Доработка после owner review

Замечания и возобновление продолжают тот же незавершённый WPLAN внутри уже разрешённого результата, путей и операций. Перерыв или рассмотрение владельцем не требуют нового WBACK, WPLAN или OD сами по себе. Изменение смысла или границы требует явного решения до новой дельты.

Завершённый WPLAN не переоткрывается. Если итерация действительно завершена, она переносится same-ID с фактическим результатом и ограничениями; новая работа получает новое разрешение. WBACK может оставаться незавершённым. Product Acceptance и выпуск — отдельные решения.


## Разделение работы и состояния

Постоянная исполняемая работа требует ровно один active `WPLAN-*.md`. При нуле первая постоянная запись нового разрешённого прохода — WPLAN по [короткой форме](../templates/workspace-plan-active.md); при двух — STOP. Исключение только для [узкой регистрации](task-intake.md#узкая-регистрация), которая не открывает исполнение.

WPLAN хранит цель, прямой запрос, действие, точные операции, обязательный результат и текущий шаг. Типизированное решение требуется по [условиям действия](../docs/technical/phase-gates.md#условия-действий). Для S1/S2 добавляются только применимые specification/design, REQ/INV/SCN, Documentation Impact и проверки по task-flow. Фаза, передача роли и четыре пустые status/ref пары не обязательны. Старые WPLAN читаются без переписывания истории.

WROAD хранит направление, WBACK — результат/DoD и его состояние, WPLAN — разрешённый проход. Ноль WPLAN означает отсутствие исполнения; несколько незавершённых WBACK допустимы. Сессия не меняет состояние продукта. Ручные counts и копии текущего маршрута не обязательны; старые проекции проверяются, если сохранены. Результат проверки записывается один раз у владельца по модели качества; текущий незавершённый шаг — в WPLAN. Применимые журналы сохраняют самостоятельный факт; повтор отчёта в roadmap, changes и sessions не требуется.

## Версии BytePress

При фиксации изменений применять [SOP версий](semver.md). Управление проектом определяет маршрут и точки контроля, а не отдельное правило увеличения версии.
