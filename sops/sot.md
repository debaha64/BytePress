# Режим источника истины

Процедура определяет действия по текущему режиму и разрешённые переходы. Единственный машинный источник состава и `sot_mode` Workspace — корневой `<Slug>.profile`. Статическая поставка не изображает развёрнутый Workspace. Workspace Update сохраняет прежний режим по [процедуре изменений](change-management.md#workspace-update).

## Выбор применимой проверки

1. Прочитать единственное поле `sot_mode` Project Profile. Допустимы только `sot_files`, `sot_git` и `sot_github`.
2. Отклонить прежнее машинное поле режима в `AGENTS.md`, даже если значение совпадает с профилем. Режима совместимости нет.
3. Применить проверку выбранного режима по [справке Git](../docs/technical/git.md). `check_workspace.py` выбирает один обработчик; `check_product.py` режим SoT не интерпретирует.
4. Отдельно проверить полномочия на последующее действие: значение режима их не создаёт.

Схема профиля принадлежит [Project Profile](../docs/architecture/project-profile.md). Точный формат `SOT_GITHUB_REPOSITORY`, поддерживаемые URL, правила `origin`, отслеживания ветви и `origin/HEAD` принадлежат [Git reference](../docs/technical/git.md#идентичность-репозитория-и-url). Это отдельная конфигурация Workspace; она не меняет схему v1.

## `sot_files`

Использовать файлы Workspace как источник текущего состояния. Не читать и не классифицировать `.git`, не требовать исполняемый файл Git, не вызывать Git CLI и не проверять удалённый репозиторий или GitHub.

Допустимая служебная копия состояния в `.git` не является источником истины, не меняет режим и исключается из обычного снимка. Её наличие не создаёт полномочий Git.

## `sot_git`

Выполнить [локальную проверку](../docs/technical/git.md#текущая-проверка-sot_git): точный корень, действительные `HEAD` и рабочая ветвь, чистое дерево, отсутствие удалённого репозитория. Историю, reflog и смысл коммитов не восстанавливать.

Режим не разрешает подключение удалённого репозитория, отправку изменений, PR, тег, выпуск или изменяющие действия GitHub. Начальная настройка отсутствующего неизменённого репозитория выполняется только по разделу ниже.

## `sot_github`

Использовать ожидаемый репозиторий GitHub как внешнюю принятую базу, а локальный Git — как рабочую копию. Сначала выполнить внешнюю подготовку, затем передать состояние [локальной проверке](../docs/technical/git.md#локальная-проверка-sot_github).

Имена ветвей, выпускные ветви, теги и GitHub Release задаёт политика репозитория и отдельные маршруты владельца. Локальный проверяющий инструмент не выполняет сеть или исправления и не подтверждает актуальность внешних сведений.

## Внешняя предварительная проверка `sot_github`

До контрольной отметки перехода:

1. Проверить действующую учётную запись, аутентификацию и ожидаемый `owner/repository` без раскрытия секретов.
2. Получить ветвь по умолчанию из метаданных репозитория GitHub.
3. Добавить или проверить единственный `origin` только в разрешённом владельцем маршруте перехода.
4. Выполнить отдельно разрешённый `fetch`.
5. Установить или обновить локальный `origin/HEAD` по полученным метаданным. Для SSH-псевдонима отдельно подтвердить, что он ведёт на GitHub, и проверить настройки, доступ и права.
6. Зафиксировать точные ссылки и передать подготовленное состояние локальному проверяющему инструменту.

`check_workspace.py` не выполняет эти внешние шаги и не утверждает свежесть метаданных.

## Начальная настройка отсутствующего репозитория

Если `sot_git` уже объявлен, а `.git/` отсутствует, агент до интервью может создать неизменённую локальную базу:

1. Подтвердить точный корень и отсутствие `.git/` без запуска инструментов Product Unit.
2. Подтвердить отсутствие продуктовых изменений.
3. Выполнить локальный `git init` с начальной ветвью, принятой текущим маршрутом.
4. Задать только локальную техническую идентичность.
5. Создать базовый коммит неизменённых файлов.
6. Проверить `HEAD`, чистое дерево и отсутствие удалённого репозитория.

Любая ошибка останавливает работу до интервью. Начальная настройка не создаёт `local_git_route` и не разрешает продуктовые изменения.

## Переход `sot_files -> sot_git`

Переход выполняется только после отдельного решения владельца. Для новой задачи принятого продукта после полного `PRODUCT_INPUT` агент один раз предлагает продолжить текущий режим, перейти в `sot_git`, отложить задачу или указать другой вариант. Порядок получения ответа принадлежит [интервью](interview.md).

Выбор перехода разрешает `sot_transition` и один `local_git_route` текущего WBACK, но не реализацию. Единая контрольная отметка перехода изменяет `<Slug>.profile:sot_mode` и сохраняет связанные IE/OD, WBACK/WPLAN и свидетельства перехода.

## Переход `sot_git -> sot_github`

Переход выполняется только из устойчивого `sot_git` и по отдельному маршруту, разрешённому владельцем:

1. Зафиксировать PASS локального `sot_git` без удалённого репозитория.
2. Выполнить внешнюю предварительную проверку, добавить канонический `origin`, получить ссылки и подготовить `origin/HEAD`.
3. Проверить идентичность репозитория, текущую и отслеживаемую ветви.
4. Единой контрольной отметкой изменить `<Slug>.profile:sot_mode` и добавить `AGENTS.md::SOT_GITHUB_REPOSITORY`.
5. Выполнить локальный `check_workspace.py` без сети.

Проверяющий инструмент не создаёт удалённый репозиторий, не выполняет `fetch` и не меняет `origin/HEAD`. Для заполненного репозитория применять [правило сохранения опубликованной истории](../docs/technical/git.md#ветви-участники-и-опубликованная-история); автоматическое присоединение независимой истории запрещено.

## Составной и обратные переходы

Атомарного `sot_files -> sot_github` нет. Пользовательский маршрут состоит из двух отдельных контрольных отметок:

```text
sot_files -> sot_git -> sot_github
```

Переходы `sot_github -> sot_git` и `sot_github -> sot_files` текущим контрактом не реализованы и требуют отдельного решения владельца. Если обратный переход будет разрешён в будущем, поле репозитория удаляется в его контрольной отметке.

## Роли и слияние

Участники и способы слияния проверяются по [контракту выпускных свидетельств](../docs/technical/release-evidence.md) в рамках [release-management](release-management.md). Общая проверка SoT не проверяет текущую учётную запись GitHub; выпускная предварительная проверка наблюдает идентичность, права и выполнимость цепочки участников, но не управляет ими или наборами правил.

Совмещение ролей допустимо только по действующим правилам. При одной учётной записи решение владельца по точному текущему SHA сохраняется в плане и свидетельствах, но не заменяет обязательную рецензию или утверждение последнего проверяемого изменения другим участником. При невыполнимой цепочке остановиться без обхода или смены правил. Новое изменение требует нового утверждения; слияние может выполнить любой разрешённый исполнитель способом, принятым для ветви. Тег и GitHub Release остаются отдельными действиями владельца. Обход правил не рекомендуется и не входит в базовый контракт.

## Защищённые поля

Точные исключения `<Slug>.profile:sot_mode` и `AGENTS.md::SOT_GITHUB_REPOSITORY` не являются постоянным разрешением `product-work`. Они допустимы только вместе с разрешённым владельцем переходом либо отдельной разрешённой процедурой миграции и с разрешением активного WPLAN.

## Маршрутное разрешение

Для одного WBACK используется не более одной записи `DECISION_KIND: local_git_route`. Только статус `active` разрешает локальную работу; `suspended`, `closed` и `revoked` не разрешают новые изменения. `ALLOWED_SURFACES` активного WPLAN остаётся более узкой границей.

## Остановка и чистое завершение

Недействительная конфигурация, репозиторий, удалённое подключение, URL, идентичность, ветвь, отслеживаемая ветвь, удалённая ссылка или `origin/HEAD`, а также грязное дерево, отставание или расхождение историй останавливают работу. Автоматические `init`, исправление удалённого подключения, `fetch`, `merge`, `rebase`, `reset` и присоединение истории запрещены.

При дефекте Harness в `product-work` агент выводит `HARNESS_BLOCKER: <краткое описание>` и прекращает изменения.

[Чистое завершение](clean-exit.md) фиксирует режим, идентичность репозитория для `sot_github`, результаты выбранной проверки, отсутствие скрытой сети и исправлений, состояние разрешения и чистоту корня. Технический PASS не является продуктовой приёмкой или полномочием на запись GitHub.
