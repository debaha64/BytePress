# Проверка работы

Целевой артефакт: `logs/quality.md`.
Шаблон или формат: `templates/quality-record.md`.
Способ записи: дозапись.

Проверки выполняются на разрешённой рабочей копии Product Unit. Если исходная поверхность защищена внешним маршрутом, используется временная копия.

```bash
python3 -m py_compile tools/bp_check.py tools/bp_clean.py
python3 tools/bp_check.py --repo .
```

К ним добавляются тесты Product Unit и проверка запуска продукта, заданные активным PLAN или продуктовым README.

Набор выбирается по риску изменения:

1. Для затронутого контракта выполняются targeted regression и обязательная локальная safety/integrity проверка.
2. Обычное завершение добавляет применимый `py_compile`, checker на свежей копии при изменении Harness-контракта, затронутые product test/smoke и необходимые fingerprints.
3. Изменение Harness, tool или test требует полного релевантного Product Unit regression suite и safety/CLI checks.
4. Предвыпускная проверка дополнительно охватывает все SoT states/transitions, product runs и release-specific checks по внешнему маршруту.

Полная tiered policy принадлежит управляющей процедуре тестов. Ни один технический уровень не создаёт продуктовую приёмку.

## Граница решения владельца

Технический PASS является свидетельством, но не означает:

1. продуктовую приёмку;
2. готовность к выпуску;
3. разрешение tag;
4. разрешение GitHub-действий.

Продуктовая приёмка требует отдельной записи `RECORD_TYPE: product_acceptance` с ID `PA-*` и точной ссылкой на ответ владельца.

## Проверка активного PLAN

Проверка подтверждает текущее состояние:

1. активный PLAN существует в количестве `0..1`;
2. фаза соответствует текущей работе;
3. `ALLOWED_SURFACES` не расширяет внешнюю границу;
4. обязательные IE, решение о реализации и продуктовая приёмка существуют, когда их требует фаза;
5. идентичность продукта согласована между кратким описанием, PLAN и корневым README;
6. для состояния с продуктом пройдены тесты Product Unit и проверка запуска продукта.

Историческая реконструкция последовательности изменений не выполняется.

## Проверка защищённых поверхностей

Канонический реестр находится в `SYSTEM.md`. В `product-work` системные поверхности не разрешаются, кроме точных `AGENTS.md::SOT_MODE` и `AGENTS.md::SOT_GITHUB_REPOSITORY`, если одна контрольная отметка перехода уже разрешена владельцем и активным PLAN.

Запрещённое изменение или дефект Harness останавливает работу. Агент выводит:

```text
HARNESS_BLOCKER: <краткое описание>
```

после чего не проектирует исправление, не запрашивает `system-editing PLAN`, не предлагает повторное исполнение, не создаёт исследование Harness и не управляет Workspace.

## Проверка DoD

[Verification Engineer](../roles/12-verification-engineer.md):

1. связывает DoD с текущим `ROAD -> BACK -> PLAN`;
2. выполняет проверки активного PLAN;
3. добавляет тесты Product Unit и проверку запуска для реализованного продукта;
4. фиксирует результат и непроверенные области в `logs/quality.md`;
5. отдельно указывает, что технический PASS не является продуктовой приёмкой.

## Одноразовые артефакты

Перед чистым завершением (`clean-exit`) проверяются:

1. exact disposable contract из `docs/technical/artifact-lifecycle.md`;
2. временные файлы и непредусмотренные остатки после cleanup;
3. наличие `research/README.md` и `research/archives/README.md`;
4. отсутствие `docs/research/` как рабочего исследовательского слоя.

## README и пользовательская граница

После появления продуктового кода корневой `README.md` содержит:

1. назначение и ценность;
2. пользователя;
3. запуск;
4. основные команды;
5. хранение данных;
6. ограничения;
7. проверки.

`docs/user/` не содержит внутренних `ROAD`, `BACK`, `PLAN` или динамического статуса Harness. Публичное описание конфигурации SoT допустимо. Для GUI-продукта технический PASS не заменяет визуальную проверку: если окно не проверено, используется статус `ready-for-owner-check`.
