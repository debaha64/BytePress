# Проверка работы

Целевой артефакт: принадлежащий Workspace `logs/quality.md`.
Шаблон или формат: `templates/quality-record.md`.
Способ записи: дозапись.

Проверки выполняются на разрешённой рабочей копии Product Unit. Если исходная поверхность защищена внешним маршрутом, используется свежая внешняя копия вне исходного Workspace. Чтение, обнаружение и разбор не запускают код продукта и отделены от явного шага исполнения.

Для внешних свидетельств до запуска фиксируют исходный манифест, очищают или явно контролируют `PYTHONPATH`, переходят в корень свежей поставки BytePress и подтверждают рабочий каталог и происхождение тестовых модулей, `new_project.py`, `project_profile.py`, `check_workspace.py`, `check_product.py` и инструмента очистки продукта. Все пути обязаны находиться внутри свежей копии и вне исходной Product Unit; иначе свидетельства недействительны. После запуска сверяют итоговый манифест и отсутствие остатков.

```bash
python3 -B -c 'from pathlib import Path; paths = (Path("tools/check_workspace.py"), Path("tools/check_product.py"), Path("tools/bp_clean.py"), Path("tools/project_profile.py"), Path("tools/new_project.py")); [compile(path.read_text(encoding="utf-8"), str(path), "exec") for path in paths]'
python3 -B -m unittest discover -s tests -p 'test_*.py'
python3 -B <external-workspace>/tools/check_workspace.py --workspace <external-workspace>
python3 -B <external-workspace>/tools/check_product.py --workspace <external-workspace>
```

Набор тестов продукта включает `test_project_profile.py`, `test_new_project.py`, `test_check_workspace.py`, `test_check_product.py`, квалификационные и остальные тесты BytePress. Проверки профиля, Project Start и проверяющих инструментов используют только нейтральные самостоятельно созданные заготовки и внешние временные копии Workspace. Они не создают корневой профиль исходной поставки и не исполняют код продукта до явного режима запуска его проверок.

Для проверки Project Start обязательны настоящие сценарии `preview/apply` нового и существующего продукта, несовпадение разрешения, исключение VCS, промежуточное создание и восстановление, регрессия TAS и создание обоих проверяющих инструментов без прежнего имени. Рабочий каталог, тестовые модули, `new_project.py`, `project_profile.py`, исполняемые файлы проверки и очистки и импортированные модули должны находиться внутри соответствующего единственного свежего корня.

Набор выбирается по риску изменения:

1. Для затронутого контракта выполняются целевая регрессия и обязательная локальная проверка безопасности и целостности.
2. Обычное завершение добавляет применимую проверку компиляции без исполнения продукта и остатков, оба проверяющих инструмента на свежем развёрнутом Workspace при изменении контракта Harness, затронутые тесты и пробный запуск продукта, а также необходимые специфические отпечатки BytePress.
3. Изменение Harness, инструмента или теста требует полного применимого регрессионного набора Product Unit и проверок безопасности и CLI.
4. Предвыпускная проверка дополнительно охватывает все состояния и переходы SoT, продуктовые прогоны и выпускные проверки по внешнему маршруту.

Виды технических свидетельств описаны в [стратегии тестирования](../docs/technical/testing.md). Ни один технический уровень не создаёт продуктовую приёмку.

## Граница решения владельца

Технический PASS является свидетельством, но не означает:

1. продуктовую приёмку;
2. готовность к выпуску;
3. разрешение тега;
4. разрешение GitHub-действий.

Продуктовая приёмка требует отдельной записи `RECORD_TYPE: product_acceptance` с ID `PA-*` и точной ссылкой на ответ владельца.

## Проверка активного WPLAN

Проверка подтверждает текущее состояние:

1. активный WPLAN существует в количестве `0..1`;
2. фаза соответствует текущей работе;
3. `ALLOWED_SURFACES` не расширяет внешнюю границу;
4. обязательные IE, решение о реализации и продуктовая приёмка существуют, когда их требует фаза;
5. идентичность продукта согласована между кратким описанием, WPLAN и корневым README;
6. для состояния с продуктом пройдены тесты Product Unit и проверка запуска продукта.

Историческая реконструкция последовательности изменений не выполняется.

## Проверка защищённых поверхностей

Канонический реестр находится в `SYSTEM.md`. В `product-work` системные поверхности не разрешаются, кроме точных `<Slug>.profile:sot_mode` и `AGENTS.md::SOT_GITHUB_REPOSITORY`, если одна контрольная отметка перехода уже разрешена владельцем и активным WPLAN.

Запрещённое изменение или дефект Harness останавливает работу. Агент выводит:

```text
HARNESS_BLOCKER: <краткое описание>
```

после чего не проектирует исправление, не запрашивает `system-editing WPLAN`, не предлагает повторное исполнение, не создаёт исследование Harness и не управляет Workspace.

## Проверка DoD

[Verification Engineer](../roles/12-verification-engineer.md):

1. связывает DoD с текущим `WROAD -> WBACK -> WPLAN`;
2. выполняет проверки активного WPLAN;
3. добавляет тесты Product Unit и проверку запуска для реализованного продукта;
4. фиксирует результат и непроверенные области в `logs/quality.md`;
5. отдельно указывает, что технический PASS не является продуктовой приёмкой.

## Одноразовые артефакты

Перед чистым завершением (`clean-exit`) проверяются:

1. точный контракт удаляемых остатков из `docs/technical/artifact-lifecycle.md`;
2. временные файлы и непредусмотренные остатки после очистки;
3. отсутствие требования подставного локального `research/` продукта в статической поставке;
4. раздельные исследования Workspace и поставляемое исследование продукта, если оно действительно часть продукта.

## README и пользовательская граница

README продукта и `docs/user` проверяются по разделу `Documentation review` ниже.

Verification Engineer независимо читает спецификацию, проектное решение, тесты, реализацию и свидетельства, не выполняет исправлений и подтверждает Impact Scan/Consistency Closure. Технический PASS подтверждает только соответствие спецификации; Validation, Product Acceptance и Release Authorization остаются отдельными состояниями.

## Переход и фактические изменения

Канонический владелец переходов — [docs/technical/phase-gates.md](../docs/technical/phase-gates.md).

Универсальный проверяющий инструмент Workspace сначала без записи выводит полную исходную базу до изменений командой `python3 -B tools/check_workspace.py --workspace <path> --print-baseline-manifest > <external-manifest>`, а после изменений вызывается с `--baseline-manifest <external-manifest>`. PASS требует канонических соседних фазы и роли, точного вида свидетельства, политики точки решения владельца и точного вида решения из одной строки перехода. Типизированные ссылки на полномочия и решение должны соответствовать границам, а фактические изменения — объявленным. WPLAN не владеет требуемым видом решения; проверяющий инструмент не принимает имя точки контроля, семейство записи или произвольное положительное значение вместо канонического вида. Отдельно зафиксировать `VERIFICATION_STATUS/REF`; `VALIDATION`, `PRODUCT_ACCEPTANCE` и `RELEASE_AUTHORIZATION` остаются `not-performed/none`, пока нет собственного полномочного свидетельства или решения.

## Выпускные свидетельства

По явно открытому внешнему маршруту отдельно проверять `release_preflight.py` и `test_release_preflight.py` из того же свежего корня; универсальный проверяющий инструмент их не вызывает. [Контракт](../docs/technical/release-evidence.md) требует тестовых заготовок и текущих наблюдений без записи, отказа в положительном результате при скрытых правилах, выполнимости цепочки участников, равенства с учётом способа переноса и независимого контрольного чтения. Автоматический `OWNER_ACTION_REQUIRED`, сверка человеком и технический PASS реализации являются разными выводами.

## Documentation review

Для S1/S2 проверить Documentation Impact и соответствие изменённых тем заявленным владельцам смысла. Объективная проверка подтверждает локальные ссылки и якоря, граф навигации и отсутствие потерянных тем, только утверждённые устаревшие формы из глоссария и заполненность решения о влиянии на документацию. Она не оценивает ясность или полноту смысла.

Человек проверяет конкретные темы:

1. понятны адресат, вопрос и результат без истории Workspace;
2. утверждения о поддерживаемых и неподдерживаемых возможностях соответствуют текущим спецификациям;
3. пользовательскому сценарию достаточно входов, действий и наблюдаемого результата;
4. тема имеет один главный предмет и полезные ссылки;
5. русский текст сохраняет условия, модальность и машинные фрагменты;
6. формы и создаваемые тексты не воспроизводят прежний контракт.

Проверяющий фиксирует замечания и проверенную область. Самопроверка агента — редакторское свидетельство; она не является независимой оценкой человеком или принятием документации владельцем. README продукта содержит назначение, пользователя, путь начала и ограничения; команды, хранение данных и проверка GUI добавляются по реальным возможностям продукта. Общие примеры WROAD и контрольной отметки допустимы при объяснении результата Project Start; текущий частный маршрут в продукте запрещён.

## Критерии по виду результата

Исследование сохраняет продуктовый контекст, фактические вопросы/решения, нерешённые пункты и решение о следующем шаге. Требования задают поддерживаемый объём, исключения, риски и ограничения. Реализация соответствует активному WPLAN и разрешённой фазе, обновляет связанные документы и явно сохраняет технический долг. Для проверки продукта отдельно фиксируются проверка только состава, разрешённые проверки средствами продукта, проверка Workspace и специфическая квалификация, если они входят в план. Эти критерии не создают следующий WPLAN, продуктовую приёмку или выпуск автоматически.
