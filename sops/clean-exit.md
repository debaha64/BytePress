# Чистое завершение

Процедура завершает проверки и передаёт зафиксированный результат. Решение о закрытии маршрута принадлежит [управлению проектом](project-management.md), структура отчёта — форме [codex-report](../templates/codex-report.md).

## Порядок

1. Завершить отдельный проход Bugfixes и Consistency Closure, затем выполнить [проверку результата](verify-work.md).
2. Проверить временные остатки и применить только разрешённую очистку по [контракту хранения артефактов](../docs/technical/artifact-lifecycle.md). Инструмент очистки не принимает решение о закрытии маршрута.
3. Зафиксировать режим Project Profile `sot_mode` и результаты применимой [проверки SoT](sot.md). В `sot_files` подтвердить, что `.git` не читался и Git CLI не вызывался. В Git-режимах сохранить проверенные факты по [справке Git](../docs/technical/git.md) и состояние единственного `local_git_route` текущего WBACK.
4. Сверить активный WPLAN, свидетельства и передачу результата по разделу ниже. После успешной технической проверки результат не должен оставаться в `implementation`: допустимы `verification`, `owner-review` или разрешённое закрытие WPLAN.
5. Подготовить отчёт по форме: выполненная работа, изменение маршрута, файлы, проверки, невыполненные действия, препятствие, открытый вопрос и следующий шаг.
6. Если постоянных изменений не было, обычный снимок не создавать. После изменений передать окончательное состояние для создания одного снимка по [выпускной процедуре](release-management.md).

## Закрытие маршрута и снимок

При разрешённом окончательном закрытии маршрутное разрешение получает `closed`. Запись сохраняется как свидетельство; она не разрешает новые коммиты и не заменяется второй записью для того же WBACK. Открытие следующего WPLAN требует собственного основания по процедуре управления проектом.

Обычный снимок создаётся после последней постоянной записи, без обычного сопроводительного файла `.sha256`. Отчёт содержит имя архива и `SNAPSHOT_SHA256`. После создания снимка Workspace не изменяется. Контрольная сумма публичного выпускного архива регулируется отдельным контрактом.

## Контрольное чтение SDLC

Перед передачей на архивацию повторно прочитать активный WPLAN и проверить:

- текущие полномочия однозначны, а контрольная отметка совпадает с маршрутом;
- ожидающая решения точка контроля не выдана за решение;
- ссылки на свидетельства и передачу результата разрешаются;
- частично выполненные изменения явно указаны;
- проверка `actual-delta` дала PASS;
- следующая роль получила один понятный вход.

Чистое завершение не меняет состояние перехода и не выполняет точку решения владельца. Технический PASS не является продуктовой приёмкой; `release/tag` и изменяющие действия GitHub требуют отдельного решения.

Выпускные свидетельства и частичное контрольное чтение передаются по [release-management](release-management.md). Отчёт сохраняет источник и дату наблюдения владельца или администратора; это наблюдение не переносится на будущую точку контроля. Сравнение без изменений не доказывает скрытое состояние правил и не разрешает повторную запись.
