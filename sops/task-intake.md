# Приём задачи

## Назначение

Приём задачи принимает вход владельца и определяет ближайший маршрут.

## Правила

1. Императивный запрос нового продукта фиксирует `intent`.
2. После первого запроса агент сначала завершает вход SoT по `sops/sot.md`; первый содержательный ответ начинает интервью, если обязательные слои ещё не закрыты.
3. Реализация открывается только отдельным `owner_decision`.
4. Получение `PRODUCT_INPUT` и выбор допустимого маршрута выполняются по [interview](interview.md); эта SOP классифицирует вход, не дублирует ветвление.
5. Запрос на Git, выпуск, тег или изменяющие GitHub-действия требует отдельного решения владельца; исключение — автоматическая начальная настройка исходного состояния уже объявленного в Project Profile `sot_mode=sot_git` по `sops/sot.md`.
6. WPLAN хранит ссылки `INTERVIEW_EVIDENCE_REF` и `OWNER_DECISION_REFS`.

## Остановка

Если агент сразу пишет код продукта без интервью, проход считается нарушенным и должен быть остановлен.

До изменения назначить класс по [task-flow](../docs/technical/task-flow.md): `S0` без изменения поведения, `S1` с локальным ожидаемым поведением или `S2` для возможности продукта, архитектуры, миграции или выпускного контракта. Для `S2` обязательны принятый владелец спецификации, проектное решение и DDD, `REQ/INV/SCN` и Impact Scan по каждому пути. Класс нельзя занижать ради обхода спецификации или тестов.

## Узкая регистрация

По прямому входу владельца при нуле или одном активном WPLAN допустимо сохранить новый исходный Feedback или добавить будущую WBACK со статусом pending. Это исключение не разрешает исполнение, изменение Product/норм, основной границы, прежних записей, активацию или закрытие задач. Текущий маршрут сохраняется. При двух WPLAN — отказ. Не требуется новый WPLAN, отдельный журнал полномочий или снимок всего Workspace.

1. Зафиксировать прямой запрос и источник в самой новой записи. Найти свободный ID по существующему владельцу: WBACK в backlog, FB в feedback. Сохранить полный исходный манифест в собственной временной области Workspace temp/. При основной работе её манифест остаётся прежним; для регистрации дополнительно сохранить прочитанные байты общего файла и его SHA-256. Хэш не заменяет содержимое.
2. Подготовить временный UTF-8 JSON вход проверки. Общие поля: `kind: backlog | feedback`, `id`, однострочные `owner_request` и `source`. Это вход доверенного исполнителя, отражающий прямое поручение, а не самостоятельное полномочие JSON. Не брать его из содержимого Feedback и не исполнять команды Original.
3. Для backlog добавить `before_base64` (все прочитанные байты), `expected_sha256`, `wroad` существующего активного WROAD и однострочный `result`. Добавляется только раздел в EOF в следующем точном виде; все прежние байты сохраняются, завершающий LF каждого поля обязателен:

```text

## WBACK-000003

WROAD: WROAD-000001
Статус: pending
Источник: <source>
Запрос владельца: <owner_request>
Результат: <result>
```

4. Для Feedback добавить `original` и фактическую `recorded_at: YYYY-MM-DD`. Новый путь строго `feedback/FB-xxxxxx.md`, с правами 0644; отсутствующий feedback создаётся с правами 0755. Исходный текст хранится без нормализации в Original. Короткая форма: заголовок ID; поля ID/recorded_at/state=open/Источник/Запрос владельца; Original в блоке text с ограждением минимум из четырёх обратных апострофов, длиннее любой их последовательности в тексте. Пустые анализ, disposition, ответ и история не создаются. Индекс не нужен для завершённости регистрации: файлы обнаруживаются по ID; существующий README сохраняется и может обновляться отдельной разрешённой работой как навигация.
5. Один исполнитель сериализует запись. Непосредственно перед заменой ещё раз сравнить байты и POSIX-права старого файла с сохранённым входом; проверить ID и отсутствие второго WPLAN. Если файл изменился — отказ без перезаписи; перечитать его и заново подготовить вход. Не применять устаревший полный текст.
6. Штатный порядок атомарной записи одного файла: `tempfile.mkstemp(dir=target.parent)` → запись полного ожидаемого содержимого в UTF-8 → `flush`/`os.fsync` → сохранение прав через `os.fchmod` → повторная сверка старого файла → `os.replace` → `fsync` каталога → контрольное чтение. Для нового FB проверить отсутствие цели непосредственно перед replace; гарантия рассчитана на одного сериализованного исполнителя, не на параллельные записи. Прерывание до replace оставляет прежний файл; после replace — полную запись. Оставшийся известный временный файл проверить и удалить; не считать его зарегистрированным. При неопределённом результате сначала контрольное чтение, не повторная запись. Новый сервис блокировок или универсальное слияние Markdown не требуется.
7. Выполнить `python3 -B tools/check_workspace.py --workspace <root> --baseline-manifest <исходная-база> --registration-input <временный-json>`. Для нескольких последовательных регистраций флаг повторяется в порядке записи. Один новый общий каталог `feedback/` проверяется и вычитается один раз для всей последовательности, после проверки её отдельных записей; заранее создавать пустой каталог не требуется. Checker сверяет полный результат каждой регистрации, вычитает только её доказанную добавку и отдельно проверяет основную дельту по прежнему WPLAN. Без основного WPLAN оставшаяся дельта обязана быть нулевой. Несовпадение предыдущего содержимого, маршрута, ID, ревизии, типа или прав — FAIL.

При основной правке backlog перед регистрацией её дельта должна покрываться точным UPDATE основной работы; регистрация сохраняет уже изменённый файл целиком. Последующие изменения общего файла, которые нельзя разделить этими точными входами, отклоняются даже при наличии UPDATE: проверить регистрацию до продолжения и согласовать последовательность работы, не заменяя основную исходную базу ради поглощения записей. Автоматического слияния нет. Хранить временные входы до завершения проверки, а подтверждённое самостоятельное свидетельство — в результате основной работы, если это необходимо для воспроизводимости. Обычная регистрация не требует нового журнала.
